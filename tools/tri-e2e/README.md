# TRI-E2E — तीनों सतहों का पूरा जुड़ा हुआ टेस्ट

> **क्या है:** एक ही रन में **एडमिन पैनल** ↔ **यूज़र पैनल (वेब)** ↔ **यूज़र पैनल (APK)** — तीनों को असली
> (live) Firebase + Supabase पर चलाकर, हर दिशा का फ़्लो साबित करना। कोई मॉक/स्टब नहीं।

---

## 1) कौन-कौन सी दिशाएँ साबित होती हैं

| # | दिशा | कैसे साबित | टेस्ट आईडी |
|---|---|---|---|
| 1 | **APK → एडमिन पैनल** | APK (असली रिलीज़ APK, एमुलेटर) में यूज़र सपोर्ट टिकट भेजता है → एडमिन पैनल की **लाइव टिकट लिस्ट** में वही टिकट थ्रेड दिखता है | `H2` ↔ `APK 3/8` |
| 2 | **एडमिन → APK** | एडमिन टिकट का जवाब देता है → APK के **My Tickets** मोडल में जवाब दिखता है | `H3` ↔ `APK 4/8` |
| 3 | **यूज़र वेब → एडमिन** | यूज़र वेब (असली साइट) से KYC (PAN/Aadhaar/नाम) जमा → एडमिन पैनल की **KYC क़तार** में वही रिक़्वेस्ट | `H8` ↔ `H9` |
| 4 | **एडमिन → यूज़र वेब** | एडमिन KYC अप्रूव करता है (सर्वर RPC) → यूज़र वेब पर **KYC Verified** दिखता है | `H9` ↔ `H11` |
| 5 | **एडमिन → दोनों (पैसा)** | एडमिन `admin_set_coins` (सर्वर, लेजर एंट्री सहित) से कॉइन देता है → यूज़र वेब **और** APK दोनों की वॉलेट UI में नया बैलेंस | `H10` ↔ `H11` ↔ `APK 5/8` |
| 6 | **एडमिन → दोनों (मैच + नोटिफ़िकेशन)** | एडमिन नया मैच + नोटिफ़िकेशन बनाता है → यूज़र वेब और APK दोनों में दिखता है | `H4/H5` ↔ `H7` ↔ `APK 6-7/8` |
| 7 | **यूज़र वेब ↔ APK एक ही हैं** | दोनों के पढ़े हुए मान (कॉइन, SD, KYC स्टेटस, टिकट जवाब, मैच नाम, नोटिफ़िकेशन) आपस में और DB से **मिलाए जाते हैं** | `compare_values.py` |

**दोनों तरफ़ के नतीजे:** होस्ट साइड `HOST-E2E-RESULT: X/12`, APK साइड `TRI-E2E-RESULT: X/8`, फिर
`CROSS-SURFACE-RESULT: N match / M mismatch`।

## 2) तीनों सतहें असल में कैसे जुड़ी हैं (तकनीकी तथ्य)

- **एक ही प्रोजेक्ट:** Firebase `fft-app-1e283` + Supabase `hddhkculuyrfoevxmlwy` — तीनों सतहें यही इस्तेमाल करती हैं।
- **लॉगिन:** यूज़र पैनल/APK का UI सिर्फ़ Google दिखाता है, पर अंदर का Firebase Auth ईमेल/पासवर्ड भी सँभालता है
  (एडमिन पैनल इसी से चलता है)। APK हार्नेस **ऐप के अपने auth ऑब्जेक्ट** से लॉगिन करता है —
  ऐप का Firebase नाम **`mainApp`** है और Auth persistence `LOCAL` (IndexedDB) है, इसलिए सेशन उसी ऐप को दिखता है।
- **एडमिन पहचान:** `admins` टेबल (uid + `is_active`) **और** `users.is_admin = true` — दोनों सर्वर-साइड चेक।
  एडमिन-ओनली RPC (`admin_set_coins`, `resolve_sd_request`, `faKYCApprove` वग़ैरह) `admin-gateway`
  एज-फंक्शन से जाते हैं जो टोकन सर्वर पर जाँचकर `admin_gateway_exec()` चलाता है।
- **नया डिवाइस गार्ड:** एडमिन पैनल नए ब्राउज़र पर "New Device Detected" ओवरले दिखाता है (ईमेल कन्फ़र्म करो) —
  ड्राइवर इसे असली UI से पार करता है।
- **पैसा:** कॉइन/डायमंड सर्वर RPC से ही क्रेडिट होते हैं (क्लाइंट बैलेंस नहीं लिखता) — `wallet_transactions`
  में लेजर पंक्ति बनती है, वही टेस्ट में जाँची जाती है।

## 4) चलाने का तरीका

**CI में:** `Build Mini eSports APK` पूरा होने पर अपने-आप चलता है (अगर उस कमिट में `tri-e2e` वाली फ़ाइल
बदली हो), या Actions → *TRI E2E (Admin Panel ↔ User Panel web ↔ APK)* → **Run workflow**।

**लोकल में (तेज़ डिबग):**
```bash
export SUPABASE_ACCESS_TOKEN=...   # SQL (management API)
export TRI_SALT=...                # QA पासवर्ड सॉल्ट
RUNID="t$(date +%H%M%S)"
node tools/tri-e2e/qa-accounts.mjs create --run $RUNID
python3 -m http.server 8099 --bind 127.0.0.1 &        # ऐप को लोकल सर्व करो
python3 tools/tri-e2e/host_driver.py --run $RUNID \
   --state tools/tri-e2e/.state/$RUNID.json \
   --out /tmp/host_out.json --shots /tmp/tri-shots --wait-apk 300 &
# दूसरे टर्मिनल/प्रोसेस में tri-e2e.html खोलो (APK में इंटेंट से, ब्राउज़र में hash-क्रेडेंशियल से)
node tools/tri-e2e/qa-accounts.mjs cleanup --run $RUNID   # अंत में सफ़ाई + residue 0
```

## 5) सफ़ाई का अनुशासन (ज़रूरी)

- हर रन का हर डेटा `QA-TEST TRI <runid>` / `QA-TRI <runid>` टैग के साथ बनता है।
- रन के अंत में (`if: always()`) वही टैग वाली सारी पंक्तियाँ + Firebase अकाउंट हटते हैं,
  फिर **residue गिनती** होती है — 0 न हुई तो स्टेप फ़ेल।
- असली यूज़र्स का पैसा/डेटा कभी नहीं छुआ जाता: क्रेडिट सिर्फ़ QA खिलाड़ी पर होता है,
  और `admin_set_coins` सर्वर-साइड है (क्लाइंट से बैलेंस नहीं लिखा जाता)।
- QA पासवर्ड सॉल्टसे बनते हैं (रैंडम नहीं) — स्टेट फ़ाइल खो जाए तो भी अकाउंट डिलीट हो सकता है।
  सॉल्ट/टोकन कभी रिपो/चैट/गिट में नहीं जाते।

## 6) जो चीज़ें अभी जान-बूझकर टेस्ट में नहीं हैं (ईमानदारी से)

- **SD (स्काई डायमंड) का स्क्रीनशॉट-डिपॉज़िट फ़्लो बंद है** — प्रोडक्शन सेटिंग `manualPayment.enabled=false`
  है (मालिक की सेटिंग, टेस्ट के लिए बदलना सही नहीं)। इसलिए पैसे की जाँच उस रास्ते से होती है जो अभी चालू है —
  एडमिन का सर्वर-साइड क्रेडिट + लेजर।
- **Paytm इंस्टेंट चेकआउट** असली पेमेंट गेटवे है — CI में नहीं चलाया जाता।
- **ग्लोबल ब्रॉडकास्ट** असली यूज़र्स को भी भेजता है — इसलिए टेस्ट में **टार्गेटेड** नोटिफ़िकेशन इस्तेमाल होती है।
